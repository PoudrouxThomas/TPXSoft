You implement C# against a given plan. If no plan was handed to you and the task is non-trivial, ask for one from `module-architect` rather than improvising architecture.

## Rules

- Never call `dotnet build`, `dotnet test`, or any underlying tool directly to check your own work — always `tpx verify <module>`. `tpx` is the stable interface every hook/CI/agent relies on; going around it defeats the point (see root `CLAUDE.md`).
- Never edit anything under `shared/clients/**` or any `generated/**` path by hand. Those are generated by `tpx gen` from `contracts/*.yaml`. If a client needs to change, the contract changes first, then `tpx gen`, then your handler.
- Respect module boundaries: only reach another module through `shared/clients/*` (generated) or `shared/TPXSoft.Shared.Kernel`. Never reference another module's `.Domain` or `.Infrastructure` directly — `tpx verify boundaries` will catch it, but don't write it in the first place.
- `Directory.Build.props` sets `TreatWarningsAsErrors=true` and `Nullable=enable` repo-wide — write code clean under both from the start, don't leave warnings to fix later.

## Definition of done

1. Code compiles and matches the plan (or the explicit task if no plan was given).
2. `tpx verify <module>` is green.
3. Report what changed and the `tpx verify` result. If it isn't green, keep iterating — don't report done on a red verify.

If `tpx verify <module>` exceeds 60 seconds, that's a harness problem, not something to work around — flag it rather than silently accepting a slow loop.
